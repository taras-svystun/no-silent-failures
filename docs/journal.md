# Journal

Newest at the bottom.

- **Plan agreed.** Full scope, 7 steps, design calls recorded in `docs/PLAN.md`.
- **Step 1: service + DB.** FastAPI tasks CRUD, one Alembic migration run by the container entrypoint, `/health` that pings Postgres (503 when it is down, checked by stopping the db container). No DB volume: the data is throwaway, so a volume would be a part with no job.
- **Step 2: metrics + Prometheus.** Middleware counts requests and times them, labelled by route template (unknown URLs go to `unmatched`, so scanners cannot create endless series). No separate error counter: errors are `status=~"5.."` on the one request counter. `db_up` gauge pings the DB on each scrape. Checked: Prometheus target `up`, `db_up` went 1 → 0 → 1 as the db container stopped and started.
- **Step 3: Grafana as code.** Provisioned Prometheus data source (fixed uid `prometheus`) and one dashboard JSON with 4 panels: request rate, error share, p95, DB up/down. Error share uses `or vector(0)`: with no 5xx ever, the error series does not exist and the panel showed "No data" instead of 0. Grafana 13 allows anonymous users only as Viewer, so login stays admin/admin and the port is bound to 127.0.0.1. Checked: `docker compose down && up` brings the dashboard back; with the db stopped, error share 0.42 and `db_up` 0 in both Prometheus and Grafana.
- **Step 4: alerts → Telegram + `/chaos`.** Four Prometheus rules (ServiceDown, DbDown, HighErrorRate > 10 %, HighLatency p95 > 0.5 s), all `for: 30s`. Alertmanager v0.34.1 sends to Telegram, with the token and chat id as Compose secrets from `.env`. `/chaos/error` raises a real exception, `/chaos/slow` sleeps. Checked: chaos loop fired HighErrorRate and HighLatency; stopping db fired DbDown; stopping app fired ServiceDown; all resolved; `alertmanager_notifications_total{integration="telegram"}` 8, failed 0. p95 showed 2.04 s for 1 s requests: `histogram_quantile` guesses inside the 1-2.5 s bucket, so it is an estimate.
- **Ports bound to 127.0.0.1.** App and Prometheus now listen only on this Mac, like Grafana and Alertmanager: on a shared Wi-Fi anyone could call `/chaos` or delete tasks. Checked: all four answer on localhost, none on the Wi-Fi IP. Also learned: after a token change in `.env`, Alertmanager must be recreated (`--force-recreate`), or it keeps the old secret file; 18 of 18 notifications failed silently until then.
- **Step 5: tests + CI.** `tests/test_api.py`: one session fixture starts `postgres:17` with testcontainers, runs the real Alembic migration, then imports the app (it reads `DATABASE_URL` at import). Six tests: create/read, update/delete, `/health` 200 on the real DB, 503 with only `db_is_up` faked, a crash counted as 500, routes labelled by template. GitHub Actions runs `pytest` on every push. Checked: 6 passed in 2.4 s; breaking the crash status, the route label and the migration each turned tests red. Swapped `httpx` for `httpx2` and the `testcontainers.community` import: both old ones print deprecation warnings.
- **Step 5 fix: list test.** `TRUNCATE` had no test that needed it (all 6 passed without it), and `GET /tasks` had no test. Added one: it lists exactly its own two tasks. Checked: 7 passed; without `TRUNCATE` it fails, seeing "buy skis" left by an earlier test.
- **Step 6: demo script.** `scripts/demo.sh` starts the stack, calls `/chaos/error` twice a second, and waits for each link with a 180 s deadline: `HighErrorRate` firing in Prometheus (`ALERTS` query), a message delivered to Telegram, chaos off, the alert gone, a second delivery. Two traps found while testing, each with its cause checked before the fix:
  - `alertmanager_notifications_total` grows before the first attempt, and `notifications_failed_total` only after all retries (9 attempts, 30 s later; Alertmanager v0.34.1 `notify/retry_stage.go`, lines 61 and 83). With a fake token the script first passed "sent" and failed only at the end. Now it counts attempts (`notification_requests_total` minus `notification_requests_failed_total`, both after Telegram answers) and stops at the first refusal: `FAILED: Telegram refused 1 send attempts`, 10 s after the alert fired.
  - A run that stops halfway leaves the alert firing; its "resolved" message came during the next run and was counted as the new "firing" (0 s instead of about 10 s). Alertmanager's groups API does not show a message still waiting (group gone at 19:25:51, message at 19:26:02). Now the script waits for a leftover alert to clear, plus one `group_interval` (30 s).
  Checked: clean run 1 min 56 s, exit 0; fake token fails at the first refusal; run started right after a leftover alert: firing delivered in 11 s, resolved in 25 s. Not checked: that the phone shows the messages (a bot cannot read its own sent messages; the counters show Telegram said OK).
